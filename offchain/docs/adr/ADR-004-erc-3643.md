# ADR-004: ERC-3643 as the Token Standard, Composed Not Reimplemented

## Status

Accepted

## Context

RWA Shift Real Estate needs a permissioned security-token standard: transfer eligibility gated by
verified on-chain identity, agent-controlled issuance/freeze/recovery, and pluggable compliance
modules (supply caps, country restrictions, etc.). Building this from scratch in Solidity would
mean re-auditing a large, security-critical surface that the industry has already standardized
and audited.

## Decision

Use **ERC-3643** (the T-REX reference implementation, `ERC-3643/ERC-3643`) unmodified as the
token layer, composed via three small RWA Shift-specific contracts
(`RwaShiftTokenFactory`, `RwaShiftIdentityGateway`, `RwaShiftDistributionRegistry`) that adapt the
platform's workflow onto T-REX's existing primitives rather than adding parallel logic. Full
rationale is in [`onchain/README.md`](../../../onchain/README.md#why-so-little-custom-solidity).

## Consequences for the off-chain platform

- The **Tokenization** unit is the only place in this codebase allowed to depend on Web3j or know
  about contract ABIs/addresses (enforced by convention + code review, not a build-time check in
  V1) — see [ADR-007](ADR-007-blockchain-source-of-truth-boundary.md).
- Off-chain eligibility logic (the `compliance` unit's `EligibilityRule`s) is advisory/UX-facing
  only: the chain's `IdentityRegistry.isVerified` is the actual enforcement point for transfers.
  Off-chain compliance state can never be "more permissive" than on-chain state in a way that
  matters, because the chain re-checks independently on every transfer.
- Country codes, wallet addresses, and opaque reference IDs are the only investor data that
  crosses the off-chain/on-chain boundary — see [ADR-008](ADR-008-offchain-pii.md).
- Smart-contract upgrade policy for the composed contracts is documented separately in
  [ADR-012](ADR-012-smart-contract-upgradeability-policy.md).
